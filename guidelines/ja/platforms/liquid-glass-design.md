# Liquid Glass の設計（Apple プラットフォーム）

## 採用方針と対象範囲

iOS 27 とネイティブの macOS 27 向けの新規アプリでは、システムのナビゲーションとコントロールを優先して Liquid Glass を採用する。標準コンポーネントで必要な操作を実現できない場合に限り、カスタムのガラス効果を追加する。最低対応 OS を iOS 27.0 または macOS 27.0 に設定し、Xcode 27 でビルドする。本ガイドラインはこの二つのプラットフォームを対象とする。

27 SDK の挙動は、2026-09-06 に入手可能なベータ版で確認した。正式版 SDK や後続の更新を採用する際は、Apple の HIG、リリースノート、SDK の宣言を再確認する。

## 操作領域とコンテンツを分ける

- Liquid Glass はコンテンツの手前にあるナビゲーションと操作領域に使う。各種バー、サイドバー、メニュー、システムの提示画面、カスタムのフローティングコントロールが対象となる。標準コンポーネントと操作中の状態に使うマテリアルはシステムに任せる。
- 背景、本文、リスト、表、コンテンツカードには、不透明な面または標準マテリアルを使う。コンテンツ内のコントロールには、操作中に一時的なガラス効果が現れる場合がある。
- 独立したガラス面を重ねない。既存のガラス面に置くコントロールには、システムの前景表現、塗りつぶし、ビブランシーを使う。
- ガラスは屈折、明るさ、色、影によって背景に適応する。フローティングコントロールの背後にもコンテンツを配置し、装飾だけを目的とした空のガラスパネルは追加しない。

## regular と clear の選択

- 通常は `.regular` を使う。文字やコントロールが多い領域に適しており、背景のぼかしと明るさを調整して読みやすさを保つ。
- `.clear` は写真や動画を中心としたコンテンツの上で使う。背景を暗くしても支障がなく、前景の文字やシンボルが太く明るいことを条件とする。regular のような可読性の自動調整は行われない。
- 明るい背景に対し、HIG は不透明度約 35% の黒いレイヤーを例示している。SwiftUI の `Glass.clear` の例では 30% を使う。いずれも調整の出発点であり、コントラストを保証する値ではない。実際の前景と動く背景を組み合わせて検証する。
- 関連する要素では同じバリアントを使い、一つのコントロール群で regular と clear を混在させない。

## ティントと前景色

- ガラスのティントは主要な操作や意味のある状態の強調に使い、補助的な操作は中立色に保つ。ブランドカラーや表現のための色は主にコンテンツに使う。
- セマンティックカラーとシステムのボタンスタイルを優先する。小さなガラスコントロールは背景に合わせて前景の明暗が変わるため、黒や白に固定したラベルはその適応を妨げる場合がある。
- 選択状態、処理の状態、破壊的な操作は、色に加えてラベル、シンボル、ボタンのロールでも示す。ティントだけで伝えない。

## 形状と同心性

- システムのコントロール形状を優先する。独立したコントロールにはカプセル形状が適している。入れ子の角丸面では、外側のコンテナーとの同心性を保つ。
- 対応 API がある場合は、同心形状の計算をシステムに任せる。再利用する形状には、角丸コンテナーの外でも使えるよう代替の半径を指定する。
- デバイスの角丸半径をそのまま写さず、画面とウィンドウの余白を守る。パディング、Dynamic Type、ウィンドウサイズが変わったら、内外の角丸を再確認する。macOS 27 ではウィンドウの角丸も変更される。

## レイアウトとスクロール端

- 背景や画像はウィンドウの端まで広げ、本文とコントロールは適切なセーフエリア内に収める。背景を全面に表示するためだけに、操作可能なビュー階層全体へ `ignoresSafeArea` を適用しない。
- スクロールエッジエフェクトで、スクロールするコンテンツとフローティングバーを区別する。通常は自動スタイルを維持し、必要な場合だけ soft または hard を指定する。同じ辺に効果を重ねず、隣接するペインでは高さをそろえる。
- 背景の延長は、サイドバーやインスペクターの背後に見せたい画像やメインコンテンツに適用する。延長される画像に文字やコントロールを含めない。
- ビューの利用可能なサイズとサイズクラスに基づいて配置する。ウィンドウが狭くなる場合、キーボードが表示される場合、文字が大きくなる場合も、主要な操作を利用できるようにする。

## アクセシビリティと検証

- 「透明度を下げる」「コントラストを上げる」「視差効果を減らす」と Dynamic Type をテストする。システムのマテリアルは設定に適応するが、独自の前景色、アニメーション、レイアウトはアプリ側で対応する。
- ライトとダークの両方で、実際の背景に対する文字のコントラストを確認する。Apple の HIG は 17 pt 以下の文字に 4.5:1、それより大きい文字または太字に 3:1 を求めている。この基準を理由に文字を小さくしたり、すべてのラベルを太字にしたりしない。
- 適切な意味を持つコントロールを使い、アクセシビリティ名と十分な操作領域を設ける。VoiceOver の読み上げ順、キーボード操作、各プラットフォームのポインターやフォーカス動作を確認する。ガラスの視覚的な反応だけではボタンの意味は付かない。
- 「視差効果を減らす」が有効な場合は、独自のモーフィングやスプリングアニメーションを抑える。アニメーションなしの状態切り替えも選択肢となる。
- 明るい背景、暗い背景、複雑な背景、動く背景に加え、小さなウィンドウ、大きな文字、非アクティブなウィンドウで確認する。実際の利用に近いコンテンツを使い、対象デバイスでスクロールと遷移の性能を測定する。

## iOS 27 と macOS 27 のシステム動作

- Liquid Glass の拡散、縁、ハイライトが調整される。システムの外観スライダーはマテリアルのティントを変えるため、独自の UI も調整範囲全体で読みやすさを保つ。
- iPad と Mac のサイドバーは端まで広がり、非アクティブなウィンドウを見分けやすくなる。ウィンドウの活動状態に連動する独自の要素には `appearsActive` を使う。
- メニューに標準で表示されるアイコンが減る。重要な操作の識別に役立つ場合だけ表示する。
- iPhone アプリは iPhone Mirroring と iPad 上でウィンドウをリサイズできる。標準のバーは自動で適応する。独自のレイアウトでは、サイズ変更やツールバーのオーバーフロー後も操作への経路を残す。
- ランタイムの変更と SDK の変更では適用条件が異なる。[API リファレンス](liquid-glass-api.md)で、シンボルの可用性と新しい実行時の挙動を区別する。
